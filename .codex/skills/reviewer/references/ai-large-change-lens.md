# AI-Generated And Large-Change Lens

Use this lens for broad diffs, AI-authored changes, large refactors, generated
artifacts, repeated mechanical edits, copied code, suspiciously fluent docs,
placeholder-heavy changes, candidate-vs-current artifact comparisons, or any
change where the risk is losing behavior in the noise.

The goal is not to punish AI output. The goal is to prevent plausible-looking
changes from passing without contract proof.

## Review Order

1. State whether coverage is complete or sampled.
2. Identify the changed public contracts and highest-risk seams first.
3. Compare before/after behavior, not formatting or fluency.
4. Build a private issue ledger for pattern breaks, stale callers, invented APIs,
   validation gaps, and removed safeguards.
5. Expand sampling where a plausible failure path appears.
6. Emit only material, reachable, evidenced findings.

## Candidate-Vs-Current Artifact Reviews

When the task asks whether a candidate is better than a current artifact:

- Name baseline and candidate explicitly.
- Classify each important delta as kept, strengthened, weakened, contradicted,
  duplicated, removed, or newly introduced.
- Do not score based on length, confidence, tone, or checklist quantity.
- A candidate is superior only if it preserves essential guardrails and adds
  behavior-changing improvements without creating contradictions or runtime
  loadability problems.
- A candidate that drops a small but critical rule is worse even if it adds many
  low-frequency bullets.
- Provide a real diff, change ledger, or concrete examples before claiming
  superiority.

## AI Hallucination And Plausibility Traps

Check for:

- invented file paths, commands, package names, exports, hooks, APIs, env vars,
  workflow permissions, config keys, or CI checks
- stale framework behavior disguised as current best practice
- generic abstractions that bypass repo-specific helpers and conventions
- wrappers that hide errors, auth, context, transaction ownership, or logs
- TODOs, placeholders, broad `any`, stubbed implementations, fake tests, and
  dead branches
- comments or docs that claim validation, rollout, approval, or compatibility
  without evidence
- broad code movement with lost import side effects, CSS scope, route metadata,
  generated output, or package initialization
- repeated mechanical edits where one pattern instance diverges in a material
  way

## Large Diff Sampling Discipline

- Prioritize public contracts, auth/data boundaries, generated/source pairs,
  migrations, workflow permissions, dependency execution, changed exported
  symbols, and cross-stack edges before repetitive churn.
- Sample representative repeated changes, then expand when an instance can break
  due to path, tenant, locale, platform, feature flag, package boundary, or
  generated contract differences.
- Do not write "reviewed all" when only sampled. State sampled surfaces,
  unreviewed surfaces, and why the highest-risk seams were selected.
- If the diff is too broad to classify central risk with available evidence, use
  `BLOCKED` or request code-mapping or specialist evidence available in the
  active runtime.

## Behavior Preservation For Refactors

- Refactors must preserve externally observable behavior unless stated intent
  says otherwise.
- Check old/new behavior for API shape, auth/permission, tenant scope, redirects,
  cache keys, generated contracts, errors, logs, metrics, retries, timeouts,
  ordering, pagination, and rollback/cleanup.
- Moved code can change import-time side effects, environment parsing, CSS load
  order, package initialization, build output, and test discovery.
- Renames need caller maps. Negative claims such as "no callers" or "all callers
  updated" require search or semantic evidence.
- Deleting code is safe only when reachability, replacement behavior, and
  generated/cached artifacts are proven.

## Generated Artifacts And Mechanical Output

- Generated output changed without source, or source changed without generated
  output, triggers the reviewer core's "broken generated-source workflow" hard
  blocker when generated integrity is central; this lens does not add a new
  blocker beyond that core rule.
- Broad generated diffs need generator version, command, source inputs, and
  downstream caller review when material.
- Do not manually edit generated files unless the repo explicitly allows it and
  the source-of-truth story is preserved.
- Snapshot/golden churn generated by broad AI changes needs semantic isolation;
  otherwise it can hide behavior changes.

## Anti-Gaming Probes

Ask these before verdict:

- Is confidence coming from current evidence, or from author seniority, AI
  fluency, previous agent ownership, narrow green tests, bot silence, or staging
  data that is not representative of production?
- If this change were approved by a less experienced reviewer, which
  merge-safety question would they most likely fail to ask? Ask it now.
- Which test could still pass if the production branch were removed?
- Which user-visible or operator-visible behavior fails within 24 hours of
  merge?
- What exact caller, route, event, queue, migration, or workflow makes this risk
  reachable?
- Did the change solve the root cause or only silence the review comment?
- Are fixtures, mocks, feature flags, snapshots, or shell scripts shaped to
  satisfy review without exercising production behavior?
- Does validation fail closed when evidence is missing?
- Did the candidate add words but weaken a decision rule?

## Reviewer Understanding Handoff

For broad, AI-authored, or multi-domain PRs, check whether the PR body,
reviewer guide, durable docs, or changed code give a future human enough context
to understand the change without trusting agent fluency. A large PR should make
the important intent and contract movement inspectable, not merely list files or
validation commands.

Flag a gap when a reviewer, operator, or future implementer would need to infer
one of these from the diff alone:

- why the change exists and which behavior is intentionally different
- which public contract, data shape, generated surface, workflow, or runtime
  mode changed
- which non-goals or old behavior should remain unchanged
- which rollout, rollback, compatibility, validation, or operator evidence
  matters for merge safety
- which generated artifacts or source-of-truth files must stay paired

Do not require a narrative for small obvious diffs. For large PRs, a missing
understanding handoff is a review issue when it can make humans merge code they
do not understand, hide contract movement, or cause future agents to preserve
the wrong behavior.

## High-Value Findings For This Lens

Formal findings are appropriate when current evidence proves one of these is
reachable:

- invented API/path/command/check controls the implementation or validation
- refactor drops behavior, auth, data scope, error mapping, or generated output
- broad change lacks enough mapping to judge central risk
- validation is theatrical and cannot fail for the changed contract
- candidate artifact is claimed superior while dropping critical guardrails
- generated/mechanical churn hides source-of-truth mismatch or unreviewed
  behavior change
