# Backend Codegen Lane

## Purpose

Own the regen workflow for every backend change that crosses a codegen boundary: SQL, mockery interfaces, or migrations. Getting the order wrong (mockery before the interface is saved, migrate before the query is regenerated) is the single most common source of silent breakage in `backend/`.

## When to apply

Apply this lane when you are about to, or just did, any of these:

- Edit `backend/internal/shared/sql/queries/*.sql` - added, renamed, or changed a query
- Add or change an interface that has a mock under `backend/internal/*/mock/` or `backend/internal/shared/*/mock/`
- Add a Postgres schema change requiring a new migration under `backend/internal/shared/sql/migrations/`
- Anything that causes `go build ./...` to fail because generated types are stale

Before editing a migration, classify the migration risk. Low-risk changes are
nullable column additions, new tables, query-only changes, and indexes that
avoid long write locks. High-risk changes include `NOT NULL` additions, column
type changes, constraint changes, data backfills, table or column drops, and
changes to large or unknown-volume tables. For high-risk changes, capture data
volume, lock risk, rollback, and rollout verification before treating the
migration design as ready.

Before deep parent-side discovery, use an available bounded read-only scout when
the current runtime exposes one and a small slice can help: map query callers,
list generated files likely to change, inspect repo-owned generation commands,
or draft narrow validation checks. Skip the scout with a concrete reason such
as a tiny edit, no exploration needed, or safety-critical migration judgment.

## Ground truth

| File                                    | Role                                                                                            |
| --------------------------------------- | ----------------------------------------------------------------------------------------------- |
| `backend/generate.go`                   | `//go:generate sqlc generate ...` + `//go:generate mockery ...` - the single regen entry point  |
| `backend/tools.go`                      | Pinned tool versions (`//go:build tools`) - `sqlc v1.30.0`, `mockery v3.6.1`, `migrate v4.19.1` |
| `backend/internal/shared/sql/sqlc.yaml` | sqlc config - `emit_interface: true`, `emit_pointers_for_null_types: true`, UUID override       |
| `backend/.mockery.yaml`                 | `all: false` - new interfaces must be added to `packages:` before generation                    |
| `backend/migrations-check.sh`           | Migration numbering/linearity check - run when any migration file changes                       |

## Workflow: adding or changing a SQL query

1. Edit the right file under `backend/internal/shared/sql/queries/`.

2. Every query must start with an annotation - `traced/sql.go` parses this for span names:

    ```sql
    -- name: GetCourseByID :one
    SELECT * FROM courses WHERE id = $1;
    ```

    Directives: `:one`, `:many`, `:exec`. Function name is PascalCase and matches the generated Go method.

3. Regenerate from `backend/`:

    ```bash
    cd <repo-root>/backend
    go generate -x ./...
    ```

    This runs both `sqlc generate` and `mockery` in that order because `generate.go` lists them that way.

4. Verify the build:

    ```bash
    cd <repo-root>/backend
    go build ./... && go vet ./...
    ```

5. Never hand-edit any file tagged `// Code generated by sqlc. DO NOT EDIT.`.

## Workflow: adding a mock for a new interface

mockery runs with `all: false`. Interfaces not listed in `backend/.mockery.yaml` will be silently skipped and nothing regenerates.

1. Add the interface under the appropriate package block:

    ```yaml
    packages:
        github.com/example-org/example-app/backend/internal/<domain>:
            interfaces:
                YourNewInterface:
    ```

2. Regenerate:

    ```bash
    cd <repo-root>/backend
    go generate -x ./...
    ```

3. Verify the generated mock landed at the expected path and the constructor is usable.

4. Never hand-edit mock files - they are overwritten on every regen.

When adding a mock to a package that already has entries in `.mockery.yaml`,
append the new interface without deleting adjacent interfaces. If two packages
use the same interface name, verify the generated mocks land in distinct package
paths and that imports still compile before treating the regen as complete.

## Workflow: creating a new Postgres migration

Migrations are embedded via `//go:embed` in `backend/internal/shared/sql/migrate.go` and run at startup by `RunMigrations`. They also run inside `testutil.DatabaseTestSuite`.

1. Create the migration pair with the correct sequential number:

    ```bash
    ls backend/internal/shared/sql/migrations/ | tail -5
    cd <repo-root>/backend
    migrate create -seq -digits 6 -ext sql \
      -dir internal/shared/sql/migrations \
      add_your_change_description
    ```

2. Write both halves. The down-migration must reverse the up-migration exactly.
   Never drop tables or columns without explicit backup or deprecation evidence.
   Prefer safe multi-step patterns for risky operations:

   - add nullable columns, backfill, then add `NOT NULL` in a later migration
   - add foreign keys as `NOT VALID`, then validate separately when appropriate
   - add large-table indexes with a write-safe strategy such as concurrent
     index creation when the migration framework supports it
   - replace risky type changes with a new column, backfill, swap, then retire
     the old column

   If row count, table size, lock behavior, or rollback safety is unknown, mark
   it `Pending Verification` and provide the exact query or staging check
   needed to verify it.

3. Verify migration linearity:

    ```bash
    cd <repo-root>/backend
    ./migrations-check.sh internal/shared/sql/migrations
    ```

4. If the migration changes a table used in queries, regenerate sqlc:

    ```bash
    cd <repo-root>/backend
    go generate -x ./...
    ```

## Verification checklist

- [ ] `cd backend && go generate -x ./...` ran and printed both `sqlc generate` and `mockery` lines
- [ ] `cd backend && go build ./... && go vet ./...` succeeds
- [ ] No hand-edits to any `// Code generated by sqlc. DO NOT EDIT.` file
- [ ] No hand-edits to any `backend/internal/**/mock/mock_*.go` file
- [ ] New interfaces appear in `backend/.mockery.yaml` before generation
- [ ] New SQL queries start with a `-- name: QueryName :one|:many|:exec` annotation
- [ ] New migrations are a matched up/down pair with linear numbering
- [ ] High-risk migrations include data-volume, lock-risk, rollback, and rollout notes
- [ ] `./migrations-check.sh internal/shared/sql/migrations` passes when migrations changed
- [ ] `cd backend && go test -run <relevant> ./internal/<domain>/...` passes

## Common failure modes

- "cannot find field X" after a SQL edit - you forgot `go generate`
- "undefined: domainmock.NewMockYourInterface" - the interface is not listed in `.mockery.yaml`
- duplicate mock types or constructors - the interface was generated twice or a
  mock path/package name collided; fix `.mockery.yaml`, then rerun
  `go generate -x ./...`
- Broken `down` migration - fix it before trusting local DB-driven tests
- Missing data-volume evidence - do not assume the migration is low-risk; record
  the exact row-count and table-size checks needed before rollout
- Direct `NOT NULL`, type-change, foreign-key, or drop migration on a large or
  unknown table - split into a safer staged migration plan
- sqlc `relation "x" does not exist` - an upstream migration is broken or out of order

## Explicit non-goals

- Do not use this lane for routine backend edits that do not cross a codegen boundary
- Do not run `mockery --all` or `sqlc generate` without `go generate`
- Do not install tool versions that differ from `backend/tools.go`
